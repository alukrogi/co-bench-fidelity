# What CO-Bench implemented for EoH and ReEvo

The released EoH adapter drops the separate natural-language description that upstream EoH passes from parent to child. The released ReEvo adapter implements both reflection levels, crossover and elite mutation, but changes how parents survive, how often the operators run and which model supplies short-term reflections. Those differences affect what the benchmark comparison measures. Their effect on the published scores is unknown. The authors explicitly disclose adapting the agents to generate complete solvers and describe selecting the best development candidate from 64 evaluations. [CO-Bench, AAAI version, “Benchmarked Methods” and “Implementation Details”](https://ojs.aaai.org/index.php/AAAI/article/download/40596/44557)

The audit follows CO-Bench’s public imports at revision `2f6620b`. The ordinary benchmark exports `ReEvo` and `EoHAgent`. The separately exported `YieldReEvo` belongs to the later FrontierCO protocol. For each original framework we inspect a public upstream revision available before the first CO-Bench preprint. This controls for later changes to the upstream implementations. The revision actually used by the CO-Bench authors remains unknown. [CO-Bench agent exports](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/__init__.py#L1-L13) · [FrontierCO instructions](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/README.md#L185-L220)

## EoH

| Mechanism | Original method and contemporary upstream release | CO-Bench release and consequence |
|---|---|---|
| Inherited representation | Each individual carries a description and executable code. In E1/E2, each parent contributes both. M1/M2 also receive both. The parser extracts the description separately. [Upstream prompts](https://github.com/FeiLiu36/EoH/blob/8d679f821af8edc7fbe3a4b6d6538b1b0362b4fb/eoh/src/eoh/methods/eoh/eoh_evolution.py#L48-L111) · [Upstream parser](https://github.com/FeiLiu36/EoH/blob/8d679f821af8edc7fbe3a4b6d6538b1b0362b4fb/eoh/src/eoh/methods/eoh/eoh_evolution.py#L121-L170) | The operator prompts still ask the model to describe its new algorithm. The active parser assigns the first extracted code block to both fields and returns before its prose-extraction code. Each ordinary evolutionary prompt interpolates parent code alone. A model can still think in prose within one response, and comments in a code block survive. The distinct heritable description is lost. [CO-Bench parser](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh/methods/eoh/eoh_evolution.py#L126-L149) · [CO-Bench operator prompts](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh/methods/eoh/eoh_evolution.py#L55-L115) |
| Operators, population and parents | The ICML study uses E1/E2 and M1/M2/M3, populations of 20 for online bin packing and 10 for TSP and flow shop, and 20 generations. The later upstream package available in February 2025 defaults to population 5, two crossover parents and E1/E2/M1/M2. [EoH, §§3–4 and Appendix D](https://proceedings.mlr.press/v235/liu24bs.html) · [Upstream parameters](https://github.com/FeiLiu36/EoH/blob/8d679f821af8edc7fbe3a4b6d6538b1b0362b4fb/eoh/src/eoh/utils/getParas.py#L13-L20) · [Operator defaults](https://github.com/FeiLiu36/EoH/blob/8d679f821af8edc7fbe3a4b6d6538b1b0362b4fb/eoh/src/eoh/utils/getParas.py#L65-L82) | The wrapper matches those upstream *package defaults*. M3 is configurable. Rank-weighted parent draws and objective-deduplicated survivors remain. The omitted default M3 alone provides weak evidence of a faulty port. [CO-Bench settings](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L65-L105) · [Selection](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L132-L189) · [M3 dispatch](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L244-L266) |
| Generational schedule | The upstream driver creates two initialization batches. Each main operator generates a population-sized batch from the same input population, then the driver merges and trims. [Upstream initialization](https://github.com/FeiLiu36/EoH/blob/8d679f821af8edc7fbe3a4b6d6538b1b0362b4fb/eoh/src/eoh/methods/eoh/eoh_interface_EC.py#L62-L74) · [Batch generation](https://github.com/FeiLiu36/EoH/blob/8d679f821af8edc7fbe3a4b6d6538b1b0362b4fb/eoh/src/eoh/methods/eoh/eoh_interface_EC.py#L218-L236) · [Survivor update](https://github.com/FeiLiu36/EoH/blob/8d679f821af8edc7fbe3a4b6d6538b1b0362b4fb/eoh/src/eoh/methods/eoh/eoh.py#L142-L165) | CO-Bench attempts ten successful initial individuals with the default size of five. Each successful evolutionary step then advances to the next operator and every feedback event trims the population, so the very next operator can use the new child. Sequential scoring alone does not require this change. A driver could freeze the parents for a batch. [CO-Bench step](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L278-L352) · [Feedback](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L384-L415) |
| Direction of fitness and final selection | CO-Bench's example feeds the normalized development score directly to its agent and describes calling `finalize()` to retrieve a candidate. The published protocol selects the highest development score. [CO-Bench driver](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/README.md#L35-L74) | `EoHAgent` defaults to minimizing that input. Its example uses raw tour lengths and the wrapper provides `get_best_algorithm()`. A caller using normalized scores needs `maximize=True` or a consistent sign conversion, plus an EoH-specific final-selection step. The private experiment settings cannot be inferred from this default. [Constructor](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L65-L91) · [Selection](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L433-L458) · [Example](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/eoh_agent.py#L535-L578) |

The AAAI paper describes EoH as evolving both thoughts and code. That characterization matters because the EoH authors tested the contribution of the two representations. On their online bin-packing setting, the three-run mean gap to the lower bound was 0.66% for EoH and 2.57% for its code-only representation variant. CO-Bench retains description requests within each completion, so that ablation does not predict the magnitude or direction of the CO-Bench effect. It does establish that inherited representation was an experimental variable in the original work. [CO-Bench, “Benchmarked Methods”](https://ojs.aaai.org/index.php/AAAI/article/download/40596/44557) · [EoH, §5.1 and Table 6](https://proceedings.mlr.press/v235/liu24bs.html)

## ReEvo

| Mechanism | Original method and contemporary upstream release | CO-Bench release and consequence |
|---|---|---|
| Initialization and parent selection | The ReEvo paper makes seed heuristics optional. Its experimental defaults use 30 initial samples, population 10, 100 evaluations, and random unequal-fitness pairs from executable individuals. The upstream driver evaluates its task-specific seed, filters failed executions, and calls `random_select`. It also defines a rank-based alternative. [ReEvo, §4 and Appendix C, Table 8](https://proceedings.neurips.cc/paper_files/paper/2024/file/4ced59d480e07d290b6f29fc8798f195-Paper-Conference.pdf) · [Seed handling](https://github.com/ai4co/reevo/blob/ec4d2a62e7f2dc2d19897a377e961de1a8930543/reevo.py#L104-L138) · [Selection](https://github.com/ai4co/reevo/blob/ec4d2a62e7f2dc2d19897a377e961de1a8930543/reevo.py#L301-L322) | The exported wrapper requests four initial samples using a generic function stub. It rank-weights pairs drawn from accumulated history. The initial four are inserted into the population and inserted again on feedback. Feedback sets execution success true even if its text describes an error. A zero score can therefore be a parent when paired with a different score. Multiple identical scores force retries and, if selection fails, a fresh generation. [Wrapper defaults](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L717-L734) · [Initialization and selection](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L269-L351) · [Feedback and insertion](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L664-L689) |
| Crossover, reflection and mutation | A generation reflects on ten pairs, produces ten crossover children and evaluates them, updates the elite, summarizes reflections, and produces five elite mutations at rate 0.5. The next population comprises those crossover and mutation offspring. The elite can be added back for selection. [Upstream mutation](https://github.com/ai4co/reevo/blob/ec4d2a62e7f2dc2d19897a377e961de1a8930543/reevo.py#L440-L458) · [Upstream loop](https://github.com/ai4co/reevo/blob/ec4d2a62e7f2dc2d19897a377e961de1a8930543/reevo.py#L460-L485) · [Defaults](https://github.com/ai4co/reevo/blob/ec4d2a62e7f2dc2d19897a377e961de1a8930543/cfg/config.yaml#L20-L26) | The adapter keeps comparative short-term and cumulative long-term reflections and passes them into generation. After ten short reflections it updates long-term memory, then samples **one** operation: elite mutation with probability 0.5, otherwise crossover on one sampled pair. The long-term summary uses all ten reflections. A fresh batch of ten reflections is elicited for the next eligible child. Thus 0.5 now controls a different choice, and a crossover child cannot become the elite for mutation in the same step. [Reflection text and memory](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L353-L415) · [Operators](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L417-L475) · [Scheduling](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L577-L625) |
| Roles, model and budget | ReEvo Appendix C uses the same model for generator and reflector by default. Upstream allows optional per-role clients. CO-Bench Fig. 3 identifies o3-mini-medium as the agents’ base. [ReEvo, Appendix C](https://proceedings.neurips.cc/paper_files/paper/2024/file/4ced59d480e07d290b6f29fc8798f195-Paper-Conference.pdf) · [Role configuration](https://github.com/ai4co/reevo/blob/ec4d2a62e7f2dc2d19897a377e961de1a8930543/cfg/config.yaml#L1-L10) · [CO-Bench Fig. 3](https://ojs.aaai.org/index.php/AAAI/article/download/40596/44557) | The default generator and long reflector use `openai/o3-mini`, while the short reflector explicitly requests `gpt-4o-mini`. The wrapper stores its `reasoning_effort` argument but only binds the model to its client, and the request helper defaults the effort argument to `None`. Actual provider effort would require receipts. Equal candidate counts do not equalize requests, tokens, latency or cost. [Request helper](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L15-L23) · [Short-reflector override](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L595-L605) · [Bound model](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/reevo.py#L717-L734) |

## What the public history establishes

1. The April 6, 2025 preprint already reports ReEvo at 0.7741 in Table 2. EoH has no agent row there. The first `agents/reevo.py` in the public default branch dates to April 16. The exact April preprint run therefore predates this public release. [Preprint v1](https://arxiv.org/html/2504.04310v1) · [First ReEvo release](https://github.com/sunnweiwei/CO-Bench/commit/c239610641b63a187be90350b4294ab05c23be3c)
2. The April adapter returns a list of strings for a single completion when `n` is omitted. Its reflection path tries to write an item of that list-valued type as text. The offline test below reaches a type error after scoring all four initial candidates. Two August 10 changes revised the reflection and response handling. This is a demonstrated obstacle to replaying the released path, with no implication about the code that actually produced the April score. [April return type](https://github.com/sunnweiwei/CO-Bench/blob/c239610641b63a187be90350b4294ab05c23be3c/agents/reevo.py#L15-L23) · [April consumer](https://github.com/sunnweiwei/CO-Bench/blob/c239610641b63a187be90350b4294ab05c23be3c/agents/reevo.py#L595-L605) · [First change](https://github.com/sunnweiwei/CO-Bench/commit/d2976deb5728b240ef225c5c6ebffb0721e6a907) · [Second change](https://github.com/sunnweiwei/CO-Bench/commit/cf119fc5c99a040fce36b6a04bb95f5f444d8bea)
3. CO-Bench added the EoH wrapper on May 29. The August 13 preprint includes EoH and per-task result tables. Those tables are evidence of reported task scores. The inspected agent releases and driver examples do not identify the EoH constructor arguments, the concrete 64 candidates, or model request receipts for individual table entries. Publication dates establish possible ordering only. [EoH wrapper release](https://github.com/sunnweiwei/CO-Bench/commit/4d6550d2c9cb517ee822592bcbd7eb10b159549e) · [v2, Appendix A](https://arxiv.org/html/2504.04310v2) · [Version dates](https://arxiv.org/abs/2504.04310)

## Offline checks

The trace invokes the released wrappers with fixed model responses and synthetic feedback. EoH receives a distinct parent-prose marker outside each code block. ReEvo receives four choices on the first request and one on all subsequent requests. Scores either increase from 1/64 through 1 or remain zero. Candidate code never runs. The experiment measures control flow and request routing. It supplies no measurements of historical scores, actual costs, or model quality. [Trace program](../scripts/trace_evolution.py) · [Recorded output](evolution-traces.json)

| Adapter and injected scores | Completed evaluations | Observed behavior |
|---|---:|---|
| EoH default, increasing | 64 | Returned score 1/64 from its best-candidate accessor. No parent-prose marker appeared in any subsequent prompt. Every surviving description equaled its candidate code. 65 calls include one connection check. |
| EoH with maximization, increasing | 64 | Returned score 1. The same parent-description loss persisted. |
| First public ReEvo, increasing | 4 | Four candidates from one generation request, followed by ten short-reflection requests. The first attempted reflection write raised a list/string type error. |
| Pinned current ReEvo, increasing | 64 | 61 generation requests, 600 short reflections and 60 long reflections: 721 requests, with 121 routed to o3-mini and 600 to gpt-4o-mini. Final population held 68 entries for 64 candidate IDs. |
| Pinned current ReEvo, all zero | 64 | 61 generation requests including the four-choice initial request. No reflections. Every attempt to obtain unequal-fitness parents after initialization fell back to fresh generation. |

## Experiments that could establish the performance impact

- **EoH inheritance.** Use the same initial candidates, generator, normalized score direction, parser for executable code and candidate budget. In paired runs change only whether the generated parent description survives and is included in the child prompt. Then vary batch timing separately. Preserve generated descriptions, parent IDs, prompts, fallback counts and scores before any test evaluation.
- **ReEvo scheduling and compute.** Compare the released stepwise loop with a queued implementation of upstream generations, feeding back one candidate at a time through the same evaluator. Keep the four initial candidates common for the schedule contrast. Vary initialization size separately. Include equal-candidate and equal-model-resource comparisons and record per-role completions, tokens and latency. Cross the short-reflector model with the scheduling change. Report all-zero or tied generations separately.
- **Historical attribution.** The smallest useful release for either method is a score-linked run manifest identifying driver revision, model settings per role, initial candidates, development outcomes, selected candidate hash and its per-instance test results. For EoH include score direction and parent descriptions. For ReEvo include pair selection, reflections and branch order. These records would distinguish an issue in the public port from one in the reported experiment.
