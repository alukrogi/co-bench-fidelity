# FunSearch, MCTS-AHD, AIDE, Chain-of-Experts and the controls

**The largest source-level discrepancy is in MCTS-AHD.** Its released wrapper selects nodes with a tree policy, then skips both mutation operators and the method’s tree-path reasoning operator. FunSearch retains its island structure while changing which programs can become parents. AIDE and Chain-of-Experts preserve substantially more of their original control logic. The public adapters support conclusions about these particular implementations. Extending an observed performance ranking to their parent frameworks requires a comparison that isolates these differences.

## What was compared

CO-Bench describes prompt and tool adaptations for end-to-end solver generation. Its loop evaluates a submitted program, feeds back the development score and feedback text, and allows early termination. Its package exports the ordinary FunSearch separately from the yield-based FrontierCO variant. This review follows the ordinary exports and compares them with framework sources available before CO-Bench’s initial April 2025 release. These upstream revisions establish a contemporaneous reference. A paper experiment could have used a different checkout or runner. [Paper, agent descriptions and implementation details](https://arxiv.org/html/2504.04310v3#Sx4) · [CO-Bench exports](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/__init__.py#L1-L13) · [Driver example](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/README.md#L43-L74)

**Interpretation.** Given 64 uniform independent island choices across ten islands, the expected number of visits to a given island is 6.4. At this scale an island may have very few distinct parent candidates. Moving to a general solver interface also removes problem-specific scaffolding that would otherwise give one method additional domain knowledge. Both choices fit a low-budget end-to-end benchmark. Scalar grouping and deterministic selection of the top clusters are separate choices and can be tested with precisely the same interface and budget. The original supplement varies skeleton, population diversity and exemplar count on one admissible-set task over five seeds. Its results motivate testing these mechanisms in CO-Bench. They give no effect estimate for CO-Bench’s 36 tasks. [FunSearch supplement, §§A.1 and E.1](https://storage.googleapis.com/deepmind-media/DeepMind.com/Blog/funsearch-making-new-discoveries-in-mathematical-sciences-using-large-language-models/Mathematical-discoveries-from-program-search-with-large-language-models.pdf)

### MCTS-AHD

**The tree is real.** CO-Bench imports the MCTS node, UCT and backpropagation implementation. It starts with an initial proposal followed by diverse proposals, maintains an elite population, converts benchmark maximization scores to the internal minimization objective, and runs an extra model call to align the description with the code. The upstream and vendored `source/mcts.py` files share Git blob `f9d0b0559c119707a50eb1c4a87925c59ec8bad7`. [Upstream tree](https://github.com/zz1358m/MCTS-AHD-master/blob/02ca64d65926fb66a871952573f9dee3375e2891/source/mcts.py#L32-L70) · [CO-Bench tree](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts/source/mcts.py#L32-L70) · [Initialization and traversal](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L198-L233) · [Description alignment](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L248-L280) · [Score conversion and feedback](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L356-L430)

**Three leaf operators never run under the default schedule.** Upstream visits a selected leaf and tries its weighted action sequence. The default sequence includes crossover `e2`, two structural mutations `m1`, two parameter mutations `m2`, and tree-path reasoning `s1` when sufficient path context exists. CO-Bench declares the same weights. Its loop returns on the first enabled action, `e2`. After feedback, the next call starts traversal again at the root. Root and non-root widening dispatch only `e1` and `e2`, respectively. The underlying mutation and path-reasoning functions are present, but none is reachable by the default scheduling path. The original study separately ablates each of these actions on TSP and knapsack. Their effects vary by task. [Original schedule](https://github.com/zz1358m/MCTS-AHD-master/blob/02ca64d65926fb66a871952573f9dee3375e2891/source/mcts_ahd.py#L164-L187) · [Path eligibility](https://github.com/zz1358m/MCTS-AHD-master/blob/02ca64d65926fb66a871952573f9dee3375e2891/source/mcts_ahd.py#L76-L88) · [Original weights](https://github.com/zz1358m/MCTS-AHD-master/blob/02ca64d65926fb66a871952573f9dee3375e2891/source/getParas.py#L15-L24) · [CO-Bench weights](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L139-L148) · [Returning inside the leaf loop](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L208-L246) · [Original paper, §5.1, Table 5 and Appendix E](https://arxiv.org/html/2501.08603v1)

**A recorded tree edge can connect programs that never shared a prompt.** Original `e2` includes the selected tree node as a parent alongside an elite individual. CO-Bench selects the best population member and a random other member, independent of the selected node. The wrapper still attaches the resulting child to that node and updates its ancestors. Tree statistics can therefore credit a branch whose code the model never saw. This changes what tree selection means, even on steps that invoke a shared operator. [Original parent construction](https://github.com/zz1358m/MCTS-AHD-master/blob/02ca64d65926fb66a871952573f9dee3375e2891/source/evolution_interface.py#L107-L125) · [CO-Bench parent construction](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L298-L350) · [Recording the child](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L462-L484)

**A reproduction needs a method-specific runner.** This wrapper defaults to `gpt-4o-mini` and 1,000 function evaluations. The paper’s o3-mini and 64 require explicit configuration or an outer cutoff. The UCT exploration term itself depends on the internal evaluation budget, so a 64-step cutoff with the internal default produces a different exploration schedule from passing `max_fe=64`. The wrapper exposes `get_best_algorithm()` and has no `finalize()` matching the common README. An adapter or runner can resolve both differences. A method-specific launch record would establish how the published evaluation did so. [Constructor defaults](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L55-L99) · [Exploration decay](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L208-L225) · [Final selection](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/mcts_agent.py#L509-L527) · [Common driver](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/README.md#L38-L74)

### AIDE

The original tree policy drafts several solutions, sometimes debugs a buggy leaf and otherwise improves the best viable node. Its own feedback model interprets execution logs and extracts a metric. The CO-Bench wrapper keeps the journal, parent selection, and draft/debug/improve dispatch. Its bundled configuration uses five initial drafts, debug probability 0.5 and maximum debug depth three. The adaptation gives the model an OR task specification and disables the original dataset preview by returning an empty string. These are concrete accommodations to a different task interface. [Original AIDE algorithm](https://arxiv.org/html/2502.13138v1) · [Original selection](https://github.com/WecoAI/aideml/blob/a4d58d94ad2035b7b458b5677c26a55e66ea8ca0/aide/agent.py#L61-L92) · [Original feedback review](https://github.com/WecoAI/aideml/blob/a4d58d94ad2035b7b458b5677c26a55e66ea8ca0/aide/agent.py#L296-L339) · [CO-Bench policy](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/aide_agent/agent.py#L60-L91) · [Configuration](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/aide_agent/utils/config.yaml#L54-L58) · [Data preview](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/aide_agent/agent.py#L273-L277)

The wrapper always assigns `gpt-4o-mini` to feedback review. It passes development feedback text as the execution output, with elapsed time set to the configured timeout and exception type set to `None`. The reviewer supplies the bug decision, summary and numeric metric used by the search policy. A timeout is described to the reviewer as an efficiency problem. The wrapper separately stores the official numeric development score and uses that for final selection. AIDE can therefore choose intermediate parents using a different metric from the one deciding the final submission. A coding step can retry up to three times to obtain a plan and code before the review call. These details matter to model and token budget comparisons. Having an LLM reviewer is faithful to AIDE’s original design. The reviewer’s identity, inputs and potential disagreement with the computed score are the quantities to log. [Wrapper model assignments, feedback and finalization](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/aide.py#L35-L72) · [Reviewer schema and metric](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/aide_agent/agent.py#L299-L377) · [Journal selection](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/aide_agent/journal.py#L172-L192) · [Generation retries](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/aide_agent/agent.py#L145-L165)

### Chain-of-Experts

The original method asks a conductor to select experts, records their comments, reduces them to code and conditionally walks backward through the experts to refine an answer after an execution failure. CO-Bench closely preserves this sequence, including the seven active expert roles and the generated test input. The internal evaluator checks whether a `solve` function executes on that input. A successful call ends its test without assessing objective quality or feasibility. The outer wrapper returns one candidate and ignores external development feedback. Its defaults permit up to eight internal trials with five consultations each. An unused `max_steps=64` argument in the internal function sets no candidate limit. [Original paper](https://proceedings.iclr.cc/paper_files/paper/2024/file/d45ee77826332c100a1e15f7765b99ff-Paper-Conference.pdf) · [Original collaboration loop](https://github.com/xzymustbexzy/Chain-of-Experts/blob/9ce1fb7e522e930fe45100ce60661a4236514de6/main.py#L35-L88) · [CO-Bench internal loop](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/chain_expert/main.py#L22-L99) · [Internal evaluator](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/chain_expert/evaluator.py#L84-L114) · [Outer wrapper](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/chain_of_experts.py#L40-L74)

The single external candidate is consistent with CO-Bench’s specific description of Chain-of-Experts and conflicts with a literal reading of its general 64-candidate statement. It also distinguishes a substantial collaborative effort from a one-call baseline. With default reflection and five consultations, the first completed trial invokes the conductor and an expert five times each, the reducer once and the internal test generator once, before any backward calls. Only an observed trace gives the realized total across trials. [Paper, benchmarked methods and setup](https://arxiv.org/html/2504.04310v3#Sx4) · [Collaboration and stop criteria](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/chain_expert/main.py#L54-L99)

There is a concrete tension between fidelity and task fit here. The original programming expert requires an LP or MIP formulation. CO-Bench retains that requirement, while its modeling expert also explicitly requests such a formulation. A consulted expert is therefore steered toward mathematical programming even on tasks where a short-budget constructive heuristic could be appropriate. The wrapper stores its timeout but does not pass it when invoking the collaboration loop. This is a credible mechanism for task-dependent differences. Quantifying it would require the sampled expert sequence, prompts, proposed solver and elapsed time. [Original programming expert](https://github.com/xzymustbexzy/Chain-of-Experts/blob/9ce1fb7e522e930fe45100ce60661a4236514de6/experts/programming_expert.py#L9-L19) · [CO-Bench programming expert](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/chain_expert/experts/programming_expert.py#L4-L16) · [CO-Bench modeling expert](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/chain_expert/experts/modeling_expert.py#L4-L15) · [Arguments forwarded](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/chain_of_experts.py#L44-L68)

### Direct Answer, BestOfN and Greedy Refinement

| Control | Behavior of the released implementation | Interpretation |
|---|---|---|
| Direct Answer | Generates a single solver, ignores feedback, returns `None` on a subsequent step and finalizes that solver. [Wrapper](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/direct_answer.py#L8-L35) | Appropriate one-shot model control. Its realized candidate count is one under the README loop. |
| BestOfN | Reuses the same task prompt without previous candidates or feedback. Stores scores and returns the highest-scoring candidate. [Wrapper](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/bestofn.py#L19-L50) | Matches the stated sampling control. The caller determines N. The class’s stored `max_iter` has no stopping effect. |
| Greedy Refinement | The first prompt matches the sampling baseline’s task instructions. Later prompts include the best-so-far code, development feedback and a request for a revised solver. The LLM may change the approach. [Wrapper](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/agents/greedy_refine.py#L27-L70) | Matches the named benchmark control. At equal scores, Python’s stable sort followed by selection of the last entry lets the latest tied candidate become the next parent. BestOfN and FunSearch use the same final tie convention. |

The most direct comparison for FunSearch is therefore a strong incumbent-refinement control with per-instance feedback and the same task interface. To isolate the value of the population, hold task prompt, candidate count and model fixed while changing parent selection. Holding token spend fixed answers a different question because prompts containing multiple complete programs cost more than single-parent prompts.

## Reproduced control-flow observations

Run from the audit root with Python 3.11+, NumPy and tqdm, and a clean CO-Bench checkout at the pinned revision.

```sh
python -B scripts/probe_frameworks.py .sources/CO-Bench
```

The probe imports the release’s FunSearch island and MCTS wrapper, including its traversal, parent selection, prompt assembly, feedback handling and tree updates. A deterministic in-memory transport replaces the model. Population-file writes go to memory. Scores are fixtures, and generated code remains unevaluated. This isolates control flow from stochastic model quality and instance difficulty. [Probe source](../scripts/probe_frameworks.py)

| Fixture | Observed result |
|---|---|
| Register A=(0,1), B=(1,0), C=(0.6,0.6), D=(0.7,0.7) in one FunSearch island, using their means as scalar scores. | Four distinct profiles formed three clusters. All 100 prompts used C and D. The top-two rule explains the exclusion of A and B on every draw. |
| MCTS, explicit 64-evaluation budget, four initial nodes, seeded permutation of positive scores 1/64 through 64/64. | 64 candidates, 128 model-transport calls. Counts were 1 `i1`, 6 `e1`, 57 `e2`, zero `m1`, `m2` or `s1`. The selected parent did not appear in the model inputs for 47 of the 57 `e2` steps. |
| MCTS, four consecutive Python float development scores of 0.0. | Step five raised `ZeroDivisionError`. The shared upstream UCT implementation divides by the observed value range, zero in this state. This is an inherited edge case. Its frequency in published runs is unknown. ## What would identify the performance effect

1. **FunSearch.** Use paired tasks and seeds to compare the released island database with per-instance signatures and probabilistic cluster sampling. Keep the end-to-end solver interface identical. Run a separately labeled scaffolded arm on tasks with published skeletons. Record accepted candidates, island visits, resets, parent IDs, development feedback and held-out scores.
2. **MCTS-AHD.** Restore the upstream action schedule with a queue that survives feedback boundaries, and include the selected node in each `e2` prompt. Vary these two changes separately. Register a zero-range UCT rule for every arm. Log actions attempted, fallback generation, tree-parent IDs, actual prompt-parent IDs, model requests and best-by-development submissions.
3. **AIDE and Chain-of-Experts.** For AIDE record reviewer model, parsed metric, official score, selected parent, bug classification and retry count. Compare the original review policy against one using the already-computed numeric score for ranking. For Chain-of-Experts publish actual external submission counts alongside internal trials, tests, forward calls and backward calls. A multi-submission variant would measure a different protocol.
4. **Budget claims.** Publish fixed-candidate and fixed-token or fixed-cost comparisons separately. Retain the one-shot controls in the figures and label their candidate counts. A historical attribution requires the runner revision, configuration, per-task trace and final-solver hash mapped to each reported row. The release’s FunSearch class dates to April 5, 2025, and its MCTS-AHD wrapper to May 29, 2025. Those dates establish artifact availability only.
