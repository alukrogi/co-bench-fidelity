# What CO-Bench measures at ten seconds

The published experiment compares development-selected Python programs under a short latency constraint across 36 tasks. The public release supports that use case in part. Its development and test observations coincide on six tasks, reference information reaches the solver on TSP, and the reported definition of normalized score differs from several task evaluators. These details affect what a score can establish even before comparing framework implementations. The checks below use the original CO-Bench evaluation entry point. The separate FrontierCO evaluator has a different interface and protocol. [AAAI paper](https://ojs.aaai.org/index.php/AAAI/article/download/40596/44557) · [arXiv v3 and Appendix A](https://arxiv.org/html/2504.04310v3) · [released CO-Bench entry point](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/README.md#L39-L81)

## Can search performance be measured on unseen instances?

**Public release.** Every call to `Evaluator.evaluate` runs all case files, normalizes results, and filters their scores into development and test feedback. The example passes only the development score and feedback to the agent. Computing both is compatible with blind model selection when the subsets are disjoint and the driver enforces this information boundary. When `get_dev` is missing, the controller substitutes a function returning `None` and each filter returns the entire result. These branches were already present in the April 2025 harness. [Evaluator](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/evaluation/evaluate.py#L54-L76) · [controller](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/evaluation/controller.py#L38-L57) · [filters](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/evaluation/utils.py#L330-L366) · [April harness](https://github.com/sunnweiwei/CO-Bench/blob/93d91b5cf86987d514fe40519245bdf6d11aea70/evaluation/utils.py)

**TSP input contract.** The TSP loader includes a reference tour as an instance field. The prompt template documents city coordinates, while the actual evaluator passes all instance fields to the submitted solver. Independently summing Euclidean distances around the released labels gives the stored reference objective to floating-point precision on all 128 size-500 and all 128 size-1000 instances. The 16 size-10000 labels are valid permutations, but their lengths range from 5,160.75 to 5,271.55 against a shared normalization value of 71.77. Their labels do not encode reference-quality answers. The presence of answer-bearing input on the first two strata makes blindness unverifiable from this public interface. The available evidence does not show that a reported agent consumed a label. The MIS loader explicitly removes graph node labels, illustrating an available control. ## Which objective is being averaged?

Equation 6 takes the smaller absolute objective divided by the larger. It is bounded by one for finite values with a positive denominator. For a solution better than a previously best-known reference, that formula decreases its score. Several released tasks instead use `reference / cost` for minimization or `value / reference` for maximization. These directional ratios reward improvements above one. Either convention can be reported explicitly. Applying the formula in the paper and applying the released task normalizers can give different rankings when references are beaten. Aircraft landing uses a shifted ratio when the reference is zero. [Equation 6](https://arxiv.org/html/2504.04310v3#Sx3.SSx2) · [current Assignment normalization](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Assignment%20problem/config.py#L175) · [MIS normalization](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Maximal%20independent%20set/config.py#L144) · [Aircraft landing](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Aircraft%20landing/config.py#L279)

**A dated reversal.** In April and August 2025, Assignment's public normalizer rewarded a higher cost for a minimization problem. For a numeric objective twice the reference, the April routine returns 2, the January 2026 correction returns 0.5, and either routine gives 1 at the reference. The authors acknowledged the scoring error and reported stopping Assignment after one round. The appendix reports 1 for every listed method on this task, which neither diagnoses the historical scoring direction nor quantifies its effect on a ranking. [April scorer](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/585d2412ced2dfd2e265606d845f67eed589bdff/Assignment%20problem/config.py#L197) · [January fix](https://huggingface.co/datasets/CO-Bench/CO-Bench/commit/604c02c7387a2471b5df397aa9a277b498261d9d) · [author reply](https://github.com/sunnweiwei/CO-Bench/issues/6#issuecomment-3736976852) · [Appendix A, Assignment](https://arxiv.org/html/2504.04310v3#A1.SSx2)

**References have different meanings.** Container loading returns the fraction of total container volume filled. A feasible packing can be optimal without filling the container. MIS uses a common reference within each graph-size stratum. Three scheduling evaluators divide the file's lower bound by the candidate makespan. A lower bound can be strictly below every feasible schedule. Comparing both fields in the held-out scheduling records shows the practical scale. The last column uses the upper bound recorded in each file. Verifying the current best feasible schedule would require separate evidence. [Container loading](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Container%20loading/config.py#L220) · [flow shop](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Flow%20shop%20scheduling/config.py#L256) · [job shop](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Job%20shop%20scheduling/config.py#L186) · [open shop](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Open%20shop%20scheduling/config.py#L186)

**Weighting.** The paper averages instances within a problem, then averages problems. The public function averages scores within a case file, then gives every file in the filtered result equal weight. On TSP, 16 instances from the size-10000 file contribute one third of the task score. Their equal-instance share would be 16/272, or 5.88%. The remaining files contain 128 each. Equal weight across sizes is a defensible target when specified. Recovering a paper-wide alternative average requires per-file or per-instance outcomes from the actual runs. The paper's Valid Solution statistic also requires every test instance of a problem to pass, making success harder on larger test sets at the same per-instance reliability. [Paper metrics](https://arxiv.org/html/2504.04310v3#Sx3.SSx2) · [public aggregator](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/evaluation/utils.py#L369-L374) · [measured group sizes and weights](evaluation-checks.json)

**Availability over time.** The MIS development map includes 100 validation graphs plus five indexed large-test graphs assigned to development. The public April and August trees omit the 100 validation files. They appear in January 2026. A reproduction from those earlier snapshots can therefore return a very different development signal from a run that had all the data. The loader traverses each graph directory without a sort and the development map uses positions. Reproductions also need a stable ordered graph manifest for the large-test split. [Development map and normalizer](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Maximal%20independent%20set/config.py#L144) · [directory traversal](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Maximal%20independent%20set/config.py#L82) · [author reply](https://github.com/sunnweiwei/CO-Bench/issues/5#issuecomment-3736955147) · [measured tree changes](evaluation-checks.json)

## What does the time limit actually cover?

The paper gives a hardware model, specifies single-core execution, reports timeouts among invalid solutions, and studies the number of agent iterations. Its neural-solver table reports objective and runtime for TSP and MIS, with different methods and problem sizes. Neither comparison is a sweep of the same CO-Bench algorithms across per-instance deadlines. The authors also replied that they had not tested a ten-minute CO-Bench budget. A common fixed limit answers an operational question about performance at that limit. The rationale about exact solutions on most instances additionally needs a denominator, representative exact methods, incumbent values, proof status and timed outcomes by instance. Failure to prove optimality by a deadline gives limited information about whether the optimal solution has already been found. [Implementation details and Figures 4–5](https://arxiv.org/html/2504.04310v3#Sx4) · [AAAI paper](https://ojs.aaai.org/index.php/AAAI/article/download/40596/44557) · [author reply](https://github.com/sunnweiwei/CO-Bench/issues/7#issuecomment-3875276329)

In the public harness, file loading happens before an instance is submitted. The child imports the task configuration, compiles the candidate, solves the instance, checks the solution, and enqueues its result. The parent starts the process and waits for `timeout + 1` seconds, which is an 11-second join argument for the nominal 10-second setting. The measured interval depends on process startup and scheduling. It includes child-side evaluation overhead and differs from a strict 10-second solver CPU clock. The release runs multiple cases concurrently, and the shown cgroup setup is commented out. No active core-affinity or solver-thread limit appears on this path. External affinity, container settings or private orchestration could have imposed the stated resource limit during the study. A reproduction needs those settings and a definition of which overheads count. [Parent and child code](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/evaluation/utils.py#L198-L286) · [parallelism](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/evaluation/evaluate.py#L25-L36) · [release environment note](https://github.com/sunnweiwei/CO-Bench/blob/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33/README.md#L137-L139)

**Classical comparison.** The authors report spending about 30 minutes per task selecting and tuning conventional solvers on development data, and give concrete examples including LKH, CPLEX and Gurobi. This is a comparator assembled under a human setup-time constraint. The code tree and HF data inspected here do not identify a complete executable 36-task classical portfolio with versions, exact models, thread limits, tuned settings and per-instance status and objective files. A common solve deadline can coexist with different formulation, import, startup, validation, incumbent-return and tuning costs. These differences remain potential explanations for a ranking until the paired baseline runs are reconstructible. [Classical baseline design](https://arxiv.org/html/2504.04310v3#Sx3.SSx1.SSS0.Px4) · [code tree](https://github.com/sunnweiwei/CO-Bench/tree/2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33) · [dataset tree](https://huggingface.co/datasets/CO-Bench/CO-Bench/tree/6e561a36254d4315b8c2d155e81a465b634e87e1)

## Independent pilot on public instances

We tested all eight held-out Assignment instances and four Set covering files chosen before running the solver, using the first numbered held-out example from each of four named OR-Library series (4, B, C, E). The sample is deliberately small and nonrandom. We held the classical solver fixed throughout. The pilot measures independent algorithms and makes no estimate of published agent performance. The observations concern two problem types on different hardware from the published study. [Pilot code](../scripts/budget_pilot.py) · [raw outcomes, input hashes, bounds and times](budget-pilot.csv)

On Assignment, SciPy's exact linear-sum-assignment routine matched every reference on instances ranging from 200 to 5,000 items. The solve, assignment conversion and bundled validity check together took 0.000879–1.035694 s per instance in this run. Parsing and imports occurred earlier. The paper's own Assignment table gives all eight listed methods the reference score, so easy exact cases are also evident in the authors' results. [SciPy algorithm](https://docs.scipy.org/doc/scipy-1.13.1/reference/generated/scipy.optimize.linear_sum_assignment.html) · [Assignment checks and references](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Assignment%20problem/config.py#L115) · [Appendix A](https://arxiv.org/html/2504.04310v3#A1.SSx2)

For Set covering, we solved a binary covering model with SciPy/HiGHS, one thread and zero relative MIP gap. Every file and budget starts a fresh optimization. The timer measures the solver call. Loading, sparse model construction and post-return validation are outside it. Budgets are internal HiGHS limits, so a call can return slightly after its nominal allowance. `limit` below means the optimizer returned an incumbent without certifying optimality before its limit. We validated every incumbent with the public CO-Bench evaluator. The experiment ran once per setting on Windows 11, AMD Ryzen 9 7945HX, one logical CPU via affinity, Python 3.12.7, NumPy 1.26.4 and SciPy 1.13.1. [Pilot implementation and emitted metadata](../scripts/budget_pilot.py) · [objective validation](https://huggingface.co/datasets/CO-Bench/CO-Bench/blob/6e561a36254d4315b8c2d155e81a465b634e87e1/Set%20covering/config.py#L200)

| Input | Rows × columns | At 1 s, incumbent / dual bound | At 3, 10 and 30 s |
|---|---:|---|---|
| scp41 | 200 × 1,000 | 429 / 429, optimal | 429, optimal |
| scpb1 | 300 × 3,000 | 69 / 65, limit | 69, optimal |
| scpc1 | 400 × 4,000 | 227 / 225, limit | 227, optimal |
| scpe1 | 50 × 500 | 5 / ≈5, optimal | 5, optimal |

All four inputs scored 1.0 at all four budgets. Two lacked certificates at one second and had certificates at three. The run demonstrates that time-to-proof can change while the reported benchmark objective stays constant. Combined with Assignment, it establishes the existence of exact cases under short compute budgets on this host. Twelve selected instances from two problems cannot estimate the fraction of the full suite solved exactly in ten seconds or the sensitivity of agent ranks. [Complete records](budget-pilot.csv)

### Reproduce

Use Python with NumPy, SciPy and psutil. The pinned fetcher retrieves 106 public files, including all task configurations, selected raw inputs and two historical configurations, and records the three dataset trees. It checks each downloaded file against its Git or LFS object digest. The deterministic check executes the public dataset loaders and extracts the upstream split and aggregation functions. The timing pilot requires CPU affinity support on the host. Commands below assume a shell at the root of this audit repository.

```sh
git clone https://github.com/sunnweiwei/CO-Bench .sources/CO-Bench
git -C .sources/CO-Bench checkout 2f6620ba5cc8d80d6fefc121b5ee2c4dcec29f33
python scripts/fetch_evaluation_inputs.py .sources/eval-replay
python -B -W ignore::SyntaxWarning scripts/check_evaluation.py .sources/eval-replay .sources/CO-Bench
python -B -W ignore::SyntaxWarning scripts/budget_pilot.py .sources/eval-replay
```

The JSON and CSV accompanying this chapter are the observed results. Timing-sensitive stopping points can vary across runs. Reconstructing the paper's ranking under a new deadline requires the selected agent programs, the baseline implementations and their historical settings.
